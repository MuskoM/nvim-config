AI Harnesses & Your Neovim

What the term actually means, why it changes where AI belongs in an editor, and 17 specific things to do to ~/.config/nvim.

Punchline, up front

The interesting work is not picking a plugin. It's building the parts of the loop your editor is uniquely good at: honest failure signals, precise context, and a review surface.

Slide 2 — the thing you already wrote

You have written a harness before

lua/custom/keymaps.lua, the <leader>cT mapping.

-- Project-wide TypeScript check: runs tsc, loads errors into quickfix
vim.fn.jobstart('yarn typecheck', {          -- 1. dispatch a tool
  cwd = project_root,
  on_stdout = function(_, data)
    vim.fn.setqflist({}, ' ', {              -- 3. write to shared state
      efm = '%f(%l\\,%c): %trror %m,...',     -- 2. parse to structure
    })
    vim.cmd('Trouble qflist open')          -- 4. surface it for a decision
  end,
})

Four steps: dispatch a tool, parse its output into structure, write that into shared state, surface it to something that can act.

Replace the thing that acts — you — with a model, and that is an agent harness. Same four steps, same order.

Which is the useful frame for the rest of this: you are not learning a new category of software. You are learning where the model plugs into a pattern you already write by hand.

Slide 3 — the concept

So what is an "AI harness"?

The term is borrowed from testing, and the analogy is exact.

The software scaffolding around a language model — tools, memory, sandboxes and feedback loops — that turns a model into an agent.

A model on its own is a pure function: tokens in, tokens out. It is stateless. It cannot read a file, run a command, remember yesterday, or stop itself. Everything an "AI agent" appears to do is done by the code around it.

That code is the harness. Just like a test harness, the interesting engineering lives in the rig, not in the thing under test.

Scaffold vs. harness — a distinction worth keeping

Scaffold How the agent is assembled, before the first prompt arrives. Tool definitions, system prompt, which model, what's mounted.
Harness Everything after: dispatching tools, compacting context, enforcing safety invariants, persisting state across turns.

People use the words interchangeably and mostly get away with it. Keep them separate when you're debugging: "bad scaffold" and "bad harness" have completely different fixes.

Slide 4 — the loop

The agent loop

One cycle. Everything else is a detail hung off it.

harnessassemble context
→
modeldecide next action
→
harnessgate & dispatch
→
worldrun tool
→
harnessfold result back in
↺

The model reads everything in its context — task, memory, prior results — and emits one decision. The harness carries it out and puts the outcome back in the context. Loop until done, blocked, out of budget, or interrupted.

The only steps the model owns

One. Decide next action. Four of the five boxes above are ordinary software, written by people, debuggable with a print statement.

Why this matters to you specifically

Improvement in daily agent output comes far more from what's in the context box and how honest the result box is than from the model. Those two boxes are exactly where an editor can help — and where a browser tab cannot.

Slide 5 — anatomy

Five layers

Every harness answers these five questions, deliberately or by accident.

LayerThe questionIn a coding agent
Tool How does it touch the world? read / write / edit, bash, grep, MCP servers, LSP
Context What does it get to see? system prompt, CLAUDE.md, file reads, diagnostics, git diff, your selection
Permission What is it allowed to do? allow/deny rules, sandboxes, approval prompts, read-only modes
Control What happens when it runs long or goes wrong? context compaction, subagents, timeouts, interrupt, budget caps
Persistence What survives the session? transcripts, memory files, git worktrees, branches

The model sets the ceiling. The harness decides how close you get to it.

Which is genuinely good news: the ceiling is not something you can move, and the gap is entirely yours to close.

Keep this table. It's the checklist for the rest of the deck — every recommendation below is one of these five layers.

Slide 6 — the shift

Your editor is no longer the harness

This is the whole reason the landscape looks confusing right now.

2022–2024 · the old shape

Editor owns the loop

AI is a feature. Inline completion, a chat sidebar. The plugin holds the API key, builds the prompt, decides what context to send.

Every editor reimplements the harness. Every editor's is worse than the last one, because it's a side quest for the plugin author.

2025–2026 · the current shape

A CLI agent owns the loop

The harness is the product, and it ships on its own release cycle. The editor becomes a peripheral: a context provider and a review surface.

Protocols appeared to formalise this — ACP · Agent Client Protocol MCP · tools & data

So "which Neovim AI plugin should I install?" is the wrong first question. The right one is: what job does nvim do inside the loop?

Three honest answers, and you can pick more than one: send precise context in (selection, diagnostics, call hierarchy), review diffs out, run the verification step. Notice that none of those require a model to live inside nvim.

Slide 9 — fix #1, do this first

Your buffers will lie to you

The single highest-value five lines in this deck.

When an agent edits a file on disk, your open buffer does not know. Neovim's autoread is on by default, but it only acts when something triggers a check — and in a terminal nvim, nothing does. So: agent writes the file → your buffer is stale → you hit :w → you silently clobber the agent's work.

-- lua/custom/autocmds.lua
vim.opt.autoread = true

vim.api.nvim_create_autocmd({ 'FocusGained', 'BufEnter', 'CursorHold', 'TermClose', 'TermLeave' }, {
  desc = 'Reload buffers changed on disk (agents write files out from under us)',
  group = vim.api.nvim_create_augroup('agent-file-sync', { clear = true }),
  callback = function()
    if vim.bo.buftype == '' and vim.fn.mode() ~= 'c' then vim.cmd('checktime') end
  end,
})

vim.api.nvim_create_autocmd('FileChangedShellPost', {
  desc = 'Say so, rather than moving the text under the cursor in silence',
  group = 'agent-file-sync',
  callback = function() vim.notify('Buffer reloaded from disk', vim.log.levels.WARN) end,
})

Your updatetime = 250 makes CursorHold fire often enough to feel live. And the FileChangedShellPost notify is not optional — a buffer that reshuffles itself without telling you is worse than a stale one.

And a trap

undofile is on, which you might assume covers you. It doesn't: external writes do not enter the undo tree. u cannot walk back an agent's edit. Git is your undo — which is the real argument for committing before you hand work to an agent, not after.

Slide 10 — fix #2, the permission & interface layer

Give the agent a namespace

And your own scheme already tells you which one.

Your rule, from the header of keymaps.lua: <leader> (,) is global — reaches outside the current buffer. <space> is this buffer, or the symbol under the cursor.

An agent reaches the whole repo, a subprocess, and the network. It is about as far outside the buffer as software gets. <leader>, unambiguously — and <leader>a is free.

Taken under <leader>: f s g c o w u R ? · taken globally under <space>: <space> a d D e f F o q v · so <leader>a collides with nothing.

KeyActionLayer
<leader>aaToggle the agent pane—
<leader>asSend selection (visual mode)context
<leader>afSend file reference at cursor linecontext
<leader>adSend diagnostics / quickfix as textcontext
<leader>agSend git diff of the working treecontext
<leader>apPrompt picker (telescope over saved prompts)tool
<leader>awWorktree switcherpersistence
<leader>axInterrupt / kill the runcontrol

Register the group label in plugins/whichkey.lua alongside Search / Git / Check: { '<leader>a', group = 'Agent' }. Your own note applies — put it in the plugin spec if it's plugin-owned, so the group disappears with the plugin.

Slide 11 — fix #3, the context layer

You already write the context file. It's just in the wrong place.

This is the most heavily-reasoned Neovim config I've read. keymaps.lua explains why localleader is also space. conform.lua explains why an Eclipse profile counts as "configured" and Spotless deliberately does not. lsp.lua explains why the capability gate was removed for jdtls.

That is exactly the content of a CLAUDE.md — and an agent cannot see a comment in a file it hasn't opened.

What to hoist to ~/.config/nvim/CLAUDE.md

  • The keymap scope rule, and the list of already-taken <space> suffixes — this is a constraint, and constraints are what agents violate when they can't see them
  • "One file per plugin in lua/custom/plugins/; mappings go in that plugin's keys = {} so lazy can defer loading"
  • Version floor: nvim 0.12+, nvim-treesitter main branch, tree-sitter-cli from brew not npm
  • "Never add format-on-save for a filetype without a project config marker" — with the reason, not just the rule
  • lua/custom/local/ is gitignored and machine-specific; never reference it unconditionally
  • House style: comments explain why, and removals are documented in place rather than deleted silently

The cheap test

Ask an agent to add a plugin with one new mapping. If it lands under the right prefix, dodges the taken suffixes, and puts the key in the spec rather than keymaps.lua — the context layer is working. If not, your CLAUDE.md is missing the sentence it needed.

Slide 12 — fix #4, the biggest lever built

Close the verification loop

<leader>cT was hardcoded to yarn typecheck. The shape was right and reusable — only the command was specific.

Where it lives — three owners

lua/custom/checks.lua          table + runner + serialiser; owns <leader>cc, <leader>cy
lua/custom/plugins/<agent>.lua owns <leader>ad and the <leader>a group; calls in
lua/custom/keymaps.lua         lost <leader>cT, kept a removal note

Its own module, not keymaps.lua — a lookup table with a job pipeline is a subsystem, not a keymap. helpers.lua is the precedent: non-plugin module, required from init.lua, registers its own mapping.

local checks = {
  java = {
    marker = { 'settings.gradle', 'gradlew' },
    cmd    = { './gradlew', 'compileJava', '-q', '--console=plain' },
    efm    = '%E%f:%l: error: %m,%W%f:%l: warning: %m,%-G%.%#',
  },
  typescript = {
    marker = { 'tsconfig.json' },
    cmd    = { 'yarn', 'typecheck' },
    efm    = '%f(%l\\,%c): %trror %m,...',
  },
}

Each row needs its own efm. That's the whole reason <leader>cT worked, and error formats don't generalise — javac's diagnostic is three lines (message, source line, caret), so %-G%.%# discards the last two or one error becomes three entries.

--console=plain is load-bearing: Gradle otherwise emits ANSI colour and progress redraws, which errorformat matches neither.

No lua row. stylua --check emits a diff with no line numbers — nothing for efm to parse. A language earns a row when its check produces positions, which is your own "prefer deleting a thing that doesn't earn its place" applied to a config table.

Two things changed in the move — both fixes, not refactors

vim.system with both streams merged. <leader>cT hooked only on_stdout. That works for tsc — but javac writes diagnostics to stderr, so the same code against a Gradle build would have reported "no errors" for a failing compile.

Exit code and parsed-entry count can disagree. A build fails for reasons efm never matches — wrong JDK, missing task, no network. A non-zero exit with an empty list now says so instead of reading as success.

The payoff

The serialiser lives in checks.lua, not in the agent's spec, so the module has zero dependency on any AI plugin. Swap CodeCompanion for sidekick and you delete one file in plugins/; this one never moves.

checks.qflist_as_text()  -- path:line:col: message, paths relative to cwd
<leader>cy           -- copies it to +, works today with no agent plugin
<leader>ad           -- the agent spec calls in, once you have one

Diagnostics are the highest value-per-token context you own. They are precise, current, and a model cannot generate them for itself.

An agent with a fast honest failure signal is a categorically different tool from one without — and it matters more than which plugin you pick.

Slide 13 — the layers nobody sets up

Control & persistence

Where almost everyone, including people who've been doing this a year, has literally nothing.

Control

Sessions outlive nvim

Run the agent in tmux or zellij, not a nvim terminal buffer. Restart nvim, the run survives. sidekick.nvim does this for you; plain tmux does it for free.

Know the stop key first

Before you need it, not while a rename is walking your repo. Bind it (<leader>ax) so it's muscle memory rather than a decision.

One task per run

Long contexts degrade. Compaction is lossy in ways you can't see. Prefer three scoped runs to one that tries to hold everything.

Persistence

Git worktrees, one per agent

Parallel work on separate branches, no branch thrash, no stash dance, no two agents editing the same file. Pairs naturally with fugitive, and it's the thing that makes "run two agents" actually workable rather than merely possible.

Commit before, not after

Because u can't undo an external write (slide 9). A clean tree before a run is your undo buffer.

Transcripts are on disk

A telescope picker over past sessions is maybe 30 lines — and you've already written custom pickers (telescope/java_symbols.lua).

Note the asymmetry: the tool layer is a crowded market with a dozen plugins competing. Control and persistence are almost entirely DIY, which is exactly why they're where the remaining upside is.

Slide 14 — brainstorm

The weird ideas

Things your particular config makes possible that a generic setup doesn't. Not all of these are good. That's the point of a brainstorm.

Worth building

jdtls call hierarchy as a context tool

<space>vc answers "how does execution actually reach this method" — in a Spring codebase, better than any grep an agent will run, and far cheaper in tokens. Serialise the Trouble buffer, send it.

kulala as the verification step

.http files are executable specs. Agent edits the endpoint → <leader>Rs → the real response goes back as context. That's a genuine test loop for API work, and you're one of very few people who already has the pieces.

Per-repo permission policy

Your conform.lua pattern — "does this project declare a style?" — generalises to "what is an agent allowed to do in this repo?". Markers in the repo, overrides in gitignored lua/custom/local/.

Interesting, probably don't

Expose your LSP as an MCP server

Hover, definition, references, call hierarchy over the wire — a running jdtls knows things static analysis of the repo doesn't. Real value, real project. Someone will ship it; it doesn't have to be you.

Agent-callable RouterOS deploy

helpers.lua could be a tool with a permission gate. Worth doing? Almost certainly not — deploying to network hardware is the wrong place to find out your permission layer has a bug. Worth knowing you could? Yes, because it's the clearest case for why that layer exists.

Symbol-picker-as-context

java_symbols.lua → pick a symbol → send definition + references. Nice, but @lsp-style providers in CodeCompanion may cover 80% of it for 0% of the work. Try theirs first.

Slide 16 — the failure modes

Anti-patterns

Don't

  • Install three AI plugins to compare them. You'll compare installers and keymaps, not workflows. Two weeks of one beats two days of three.
  • Treat inline completion and agents as the same category. Different loop, different context strategy, different failure modes. The arguments about "AI in the editor" mostly collapse once you separate them.
  • "Fix" your conform gating so format-on-save always runs. It's currently protecting you from fighting an agent over whitespace.
  • Auto-approve everything to cut friction. The permission layer is load-bearing. Reduce the friction by narrowing scope, not by removing the gate.

Instead

  • More context is not better context. Ten lines of real diagnostics beat a thousand lines of repo dump, and the dump actively crowds out what matters.
  • Optimise the boxes you own. Four of the five boxes in the loop are ordinary software. That's where your improvements are.
  • Commit before you delegate. Cheapest safety mechanism in the whole stack, and it's the one that makes everything else recoverable.
  • Write down invariants where the agent can read them. You already write them. Move them.

The plugin is a thin adapter. The harness is where the work is — and right now, the harness is mostly yours to build.
